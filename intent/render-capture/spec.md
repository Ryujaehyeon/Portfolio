## 한 줄 요약

`-smoke -shot <폴더>` 로 실행하면 시드와 프레임 시간을 고정해 매번 같은 장면을 만들고, 정해 둔 프레임마다 화면을 PNG 로 저장한다.
저장한 두 폴더는 비교 스크립트로 픽셀 단위 비교한다.

## 요구사항

| ID | 요구사항 | 판정 방법 |
|---|---|---|
| R1 | **결정적 실행 모드.** 명령줄에 `-shot <폴더>` 가 있으면 켜진다. 켜지면 난수 시드를 고정값(1)으로 두고, `CTimeMgr::DeltaTime()` 이 실제 경과 시간 대신 항상 1/60 초를 돌려준다 | 코드 검토 |
| R2 | **게임 시계.** 스모크 일정(스테이지 진입 후 몬스터 확인·종료, 몬스터 처치, 스킬 시전)이 실제 시간 대신 `GameTickMs()` 를 쓴다. 이 함수는 평소에는 `GetTickCount64()` 와 같고, 결정적 모드에서는 「지나간 프레임 수 × 1000/60」을 돌려준다. 스모크 전체 제한 시간(30초)은 안전장치라 실제 시간을 유지한다 | 코드 검토 |
| R3 | **캡처 시점.** 장면마다 「그 장면에 들어온 뒤 몇 번째 프레임인지」로 캡처 시점을 정한다. 시점 목록은 한 곳(표)에 둔다. 장면 0·1 에서 한 장씩, 장면 2 에서 몬스터와 부딪힌 뒤·스킬 시전 중·처치 뒤를 포함해 네 장 안팎 | 코드 검토 |
| R4 | **캡처.** 그 프레임을 다 그린 뒤 `Present` 직전에 백버퍼를 읽어 `<폴더>/s<장면>_f<프레임 4자리>.png` 로 저장한다. 저장에 실패하면 스모크 로그에 `FAIL capture ...` 를 남긴다 | 실행 |
| R5 | **재현성.** 같은 빌드로 두 번 실행한 캡처 폴더를 비교하면 모든 이미지가 완전히 같다(다른 픽셀 0) | 비교 스크립트 |
| R6 | **비교 스크립트** `scripts/compare-shots.ps1 -Expected <폴더> -Actual <폴더> [-Tolerance <채널 차이>] [-MaxRatio <비율>]`. 이미지마다 다른 픽셀 비율과 최대 채널 차이를 출력하고, 다른 곳을 표시한 diff 이미지를 `<Actual>/diff/` 에 만든다. 한쪽에만 있는 파일도 실패로 보고한다. 모두 허용 범위면 종료 코드 0, 아니면 1 | 실행 |
| R7 | **기존 동작 유지.** `-shot` 이 없으면 시드·프레임 시간·스모크 일정이 지금과 같다. 기존 스모크가 4개 구성에서 PASS | CLAUDE.md |
| R8 | 경고 0. 캡처 폴더는 gitignore. CLAUDE.md 「테스트」에 사용법 | 빌드·문서 검토 |

## 설계

### 결정적 실행에 필요한 것

같은 장면을 재현하려면 「시간」과 「난수」 두 가지만 고정하면 된다. 조사한 결과 장면 진행은 모두 다음 셋 중 하나에서 나온다.

| 원천 | 지금 | 결정적 모드 |
|---|---|---|
| 난수 | `srand(time(0))` — 몬스터 위치·방향·이동 거리, Blizzard 흩뿌림 | `srand(1)` |
| 프레임 시간 | `CTimeMgr` 가 `QueryPerformanceCounter` 로 실제 경과 시간을 잼 — 애니메이션·이동·메뉴 진입 대기(1초) | 항상 1/60 초 |
| 스모크 일정 | `GetTickCount64` 기준(스테이지 진입 1초·4초, 몬스터 처치 1.5초, 스킬 시전 2초) | `GameTickMs()` — 프레임 수로 계산 |

로딩 스레드는 없다. 사용자 입력은 스모크가 이미 막는다(smoke-input-isolation).

### 모드 상태를 어디에 두나

`Headers/SmokeLog.h` 의 방식을 따른다. 헤더 전용 함수 안의 static 상태 하나에 「결정적 모드인가, 캡처 폴더, 지나간 프레임 수, 장면별 프레임 수」를 둔다.
Client 메인 루프가 프레임마다 한 번 프레임 수를 올린다. 결정적 모드 판정은 `IsFixedStepMode()` 하나로 한다.

### 캡처를 언제 하나

백버퍼 내용은 `Present` 뒤에는 보장되지 않는다(`D3DSWAPEFFECT_DISCARD`). 그래서 `CDevice::Render_End` 에서 `EndScene` 다음, `Present` 바로 앞에 저장한다.
캡처 요청은 메인 루프가 시점 표를 보고 `CDevice` 에 「이번 프레임 끝에 이 경로로 저장」을 걸어 두는 방식이다. 이렇게 하면 Engine 은 「언제」를 몰라도 된다.

D3D9 에서 저장하는 순서:
1. `GetBackBuffer` 로 백버퍼를 얻는다.
2. 같은 크기·형식의 시스템 메모리 표면에 `GetRenderTargetData` 로 복사한다.
3. `D3DXSaveSurfaceToFile(PNG)` 로 저장한다.

2단계(`render-backend`)에서 이 기능은 렌더러 인터페이스의 `SaveBackBuffer` 로 옮겨지고, 3·4단계의 D3D11 백엔드도 같은 함수를 구현한다.

### 비교 스크립트

- Windows PowerShell 5.1(`powershell.exe`)에서 돈다. WSL 에서도 그대로 부를 수 있다.
- 픽셀 비교는 PowerShell 반복문으로는 느리다(800×600 한 장에 48만 픽셀). 그래서 C# 코드를 `Add-Type` 으로 넣어 `LockBits` 로 한 번에 비교한다. 외부 도구는 필요 없다.
- 「다름」의 기준: 픽셀의 R·G·B 중 하나라도 차이가 `Tolerance` 를 넘으면 다른 픽셀이다. 이미지의 다른 픽셀 비율이 `MaxRatio` 를 넘으면 실패다.
  알파는 비교하지 않는다 — 백버퍼의 알파는 화면에 보이지 않고, 블렌딩 결과로 남는 값이 백엔드마다 다를 수 있다.
  기본값은 둘 다 0(완전 일치). D3D9 와 D3D11 비교처럼 텍스처 필터링 차이가 예상될 때만 값을 준다.
- diff 이미지는 같은 픽셀을 어둡게, 다른 픽셀을 빨강으로 칠한다. 어디가 다른지 한눈에 보인다.

## flag된 우려사항

| 무엇이 | 어느 기준에 | 해소 |
|---|---|---|
| 프레임 시간을 고정하면 게임이 실제보다 빨리(또는 느리게) 진행된다 | 의미 | 캡처 모드에서만이다. 화면 비교에는 「같은 상태」가 중요하고 실제 속도는 상관없다 |
| 숨은 비결정 요소(초기화 안 된 메모리, 주소 순서에 기댄 반복 등)가 남아 있을 수 있다 | 재현성 | R5 로 확인한다. 실패하면 그 원인을 이 인텐트 안에서 고친다(member-init 으로 초기화 문제는 이미 줄었다) |
| 캡처 시점이 장면 진입 프레임 기준이라, 장면 진입이 한 프레임만 밀려도 모든 캡처가 밀린다 | 비교 안정성 | 장면 진입도 결정적이므로 같은 빌드에서는 밀리지 않는다. 다른 백엔드와 비교할 때는 같은 로직을 쓰므로 역시 같다 |
