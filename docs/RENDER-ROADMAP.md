# 렌더링 전환 로드맵 — D3D9 에서 D3D11 로

이 문서는 렌더링을 Direct3D 9 에서 Direct3D 11 로 옮기는 네 개의 인텐트를 한데 묶어 설명한다.
각 단계의 자세한 요구와 작업 순서는 단계별 `intent/<슬러그>/` 문서에 있고, 여기서는 **왜 이렇게 나누었는지**와
**단계들이 서로 어떻게 이어지는지**를 다룬다.

## 1. 목표

두 가지를 함께 이룬다.

1. **구조**: 게임 코드가 특정 그래픽 API 에 묶이지 않게 한다. 렌더러를 인터페이스 뒤로 숨겨 두면
   D3D9·D3D11 을 골라 쓸 수 있고, 나중에 다른 구현(예: D3D12)도 같은 자리에 끼울 수 있다.
2. **학습**: D3D11 스프라이트 렌더링 파이프라인을 **직접** 구현해 보며 이해한다.
   이를 위해 Microsoft 의 DirectXTK 로 먼저 「정답이 되는 구현(B)」을 만들어 두고, 그 옆에 직접 구현(A)을 단계별로 쌓는다.

## 2. 단계 한눈에 보기

| 순서 | 슬러그 | 하는 일 | 동작 변화 | 누가 |
|---|---|---|---|---|
| 1 | [`render-capture`](../intent/render-capture/intent.md) | 같은 장면을 매번 똑같이 재현하는 실행 모드와 화면 캡처·비교 도구 | 없음(새 실행 옵션만) | Claude |
| 2 | [`render-backend`](../intent/render-backend/intent.md) | 렌더러 인터페이스를 만들고 지금의 D3D9 코드를 그 뒤로 옮긴다 | 없음(픽셀 단위로 같음) | Claude |
| 3 | [`render-dxtk`](../intent/render-dxtk/intent.md) | D3D11 + DirectXTK 백엔드(B). `-d3d11` 로 선택 | 새 백엔드 추가 | Claude |
| 4 | [`render-guide`](../intent/render-guide/intent.md) | 직접 구현할 뼈대(A)와 단계별 가이드 문서, 검증된 정답 | 새 백엔드 뼈대 추가 | Claude → **사용자가 구현** |
| 이후 | (미정) | 수학 라이브러리 교체, D3D9 제거 여부, 툴의 D3D11 전환 | — | 필요할 때 결정 |

```
 render-capture ──▶ render-backend ──▶ render-dxtk(B) ──▶ render-guide(A 뼈대·가이드)
   비교 기준 마련       구조 정리           정답 구현            사용자가 A 를 직접 구현
        │                   ▲                   ▲                         │
        └───── 각 단계의 화면이 앞 단계와 같은지 판정 ─────────────────────┘
```

## 3. 왜 이 순서인가

**비교 도구가 맨 앞에 오는 이유.** 렌더링 변경은 「돌아가기는 하는데 미묘하게 다르게 그려지는」 회귀가 가장 흔하다.
스모크는 게임 로직만 판정하므로 이런 회귀를 잡지 못한다. 같은 장면을 매번 똑같이 재현해 캡처하고 이미지를 비교하는 도구가 있어야
2단계에서는 「픽셀 하나 다르지 않다」를, 3·4단계에서는 「D3D9 와 같은 그림이다」를 객관적으로 판정할 수 있다.

**인터페이스가 D3D11 보다 먼저인 이유.** 지금 게임 코드 77곳이 `ID3DXSprite` 를 직접 부른다.
이 상태에서 D3D11 을 넣으면 같은 77곳을 다시 고쳐야 한다. 먼저 호출부를 인터페이스 하나로 모아 두면,
그 뒤로는 구현을 추가해도 게임 코드를 건드리지 않는다(개방 폐쇄 원칙).
구현이 하나뿐일 때 인터페이스를 만드는 것은 보통 성급한 추상화지만, 이번에는 두 번째·세 번째 구현(B·A)이 바로 뒤에 확정되어 있다.

**B 가 A 보다 먼저인 이유.** 직접 구현을 처음 배울 때 가장 힘든 것은 「화면이 이상한데 무엇이 정답인지 모르는」 상태다.
B 가 먼저 있으면 A 의 결과를 B 와 나란히 비교할 수 있고, 막히면 DirectXTK 소스에서 같은 일을 하는 부분을 찾아볼 수 있다.

## 4. 지금 코드에서 출발점

조사로 확인한 사실이다(경로는 `2D-Portfolio/` 기준).

- **그리기 호출의 형태가 하나뿐이다.** `SetTransform(월드 행렬)` 다음에 `Draw(텍스처, 원본 사각형 또는 NULL, 중심점, NULL, 색)`.
  Client 66곳, 툴 12곳. 이 단순함 덕분에 인터페이스를 작게 만들 수 있다.
- **월드 행렬은 크기·Z 회전·이동만 쓴다.** 2D 아핀 변환이라 D3D11 에서도 그대로 재현할 수 있다.
- **그리는 순서 = 제출한 순서.** `D3DXSPRITE_ALPHABLEND` 만 쓰고 정렬 플래그가 없다. 그리는 순서는 `CSortMgr` 의 레이어 순서가 정한다.
- **텍스처**: png 8,029개, bmp 183개, jpg 2개. 원본 크기 그대로, 밉맵 1단계로 적재하며 적재할 때 컬러키로 투명 처리한다
  (Client 의 여러 장 텍스처는 검정, 그 밖에는 흰색).
- **크기 정보** `TEXINFO::ImgInfo.Width/Height` 를 Client·툴 62곳에서 읽는다.
- **툴**은 장치 하나로 두 창(메인 뷰·미니맵)에 그린다. D3D11 에서는 창마다 스왑체인이 따로 필요해 구조가 달라진다 — 이번 범위에서 툴은 D3D9 를 유지한다.
- **같은 장면 재현이 아직 안 된다.** 난수 시드가 현재 시각이고(`srand(time(0))`), 프레임 시간이 실제 경과 시간이며,
  스모크의 일정(스킬 시전 등)도 실제 시간 기준이다. 1단계가 이것을 해결한다.

## 5. 정해 둔 결정

| 결정 | 내용 | 이유 |
|---|---|---|
| D3D9 백엔드 | 유지하고 기본값으로 둔다 | 비교 기준이고, 툴이 계속 쓴다. 제거는 이후에 판단 |
| 툴 | D3D9 유지 | 창 두 개라 스왑체인 구조가 다르고, A 학습과 관계가 없다 |
| 백엔드 선택 | 실행 인자(`-d3d11`, `-d3d11custom`) | 같은 빌드로 비교할 수 있다 |
| 백엔드 생성 위치 | 앱이 만들어 Engine 에 넘긴다 | 툴이 D3D11·DirectXTK 를 링크하지 않아도 된다(앱마다 다른 것은 앱이 정한다는 기존 원칙) |
| D3D12 | 이번에는 하지 않는다 | 2D 스프라이트에는 이득이 거의 없고, 지금 맞추면 인터페이스가 복잡해진다. 인터페이스는 나중에 추가하는 것을 막지 않는다 |
| 수학(`D3DXVECTOR3`·`D3DXMATRIX`) | 이번에는 그대로 둔다 | 약 250곳에 걸친 별개의 일이다. 그리기 변경과 섞으면 회귀 원인을 가리기 어렵다 |
| A 의 정답 코드 | 가이드 본문과 분리해 제공한다 | 스스로 짜 보되, 막히면 확인할 수 있게 |

## 6. 용어

| 용어 | 뜻 |
|---|---|
| 백엔드 | 렌더러 인터페이스를 실제 그래픽 API 로 구현한 것. 여기서는 D3D9·D3D11(B)·D3D11(A) |
| B / A | B 는 DirectXTK 의 `SpriteBatch` 로 만든 D3D11 백엔드, A 는 같은 일을 D3D11 API 로 직접 짠 백엔드 |
| 스왑체인 | 화면에 내보낼 백버퍼들을 관리하는 DXGI 객체. 그린 뒤 `Present` 로 화면에 보낸다 |
| SRV | Shader Resource View. 텍스처를 셰이더가 읽을 수 있게 해 주는 「보기」 |
| 배칭 | 같은 텍스처를 쓰는 사각형 여러 개를 버퍼 하나에 모아 그리기 호출 한 번으로 그리는 것 |
| 결정적 실행 | 같은 입력이면 매번 같은 프레임에 같은 상태가 되는 실행. 화면 비교의 전제 |
