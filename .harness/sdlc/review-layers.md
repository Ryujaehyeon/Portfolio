# 코드 리뷰 원칙 (레이어별)

> Claude Code 팀의 코드 리뷰 방식을 레이어로 정리했다. 리뷰를 수행하거나 리뷰 체계를 설계할 때 기준으로 쓴다.
> 저장소별 리뷰 규정(무엇이 Important인가, 제외 경로 등)은 [templates/REVIEW.md](../templates/REVIEW.md)에 둔다.

| 레이어 | 이름 | 판별 질문 |
|---|---|---|
| 1 | 사전 검증 | PR 전에 **실행 결과**로 동작을 보였는가? |
| 2 | AI 리뷰 | 변경이 문제를 풀고, 시스템에 맞고, 다른 것을 깨지 않는가? |
| 3 | 보안 리뷰 | 열린 보안 지적이 **모두 해소**되었는가? |
| 4 | 자동 검사 | CI(린트·타입·테스트·빌드)가 통과했는가? |
| 5 | 사람 승인 | **변경의 위험도**에 맞는 사람이 승인했는가? |
| 6 | 머지 큐·플래그 | main에 합쳐도 깨지지 않고, 단계적으로 내보내는가? |
| 7 | 감지·롤백 | 잘못되면 빨리 알아채고 **한 단계로** 되돌릴 수 있는가? |

각 레이어는 서로 다른 곳에 구멍이 있다. 한 레이어가 놓친 것을 다음 레이어가 잡고, 모두를 통과한 것은 롤백이 처리한다.
"사람이 코드를 읽었는가"가 아니라 "이 변경에서 무엇이 잘못될 수 있고, 어느 검사가 그것을 잡기에 맞는가"를 묻는다.

---

## 1. 사전 검증 — PR 전에

- 에이전트에게 실행 가능한 검증 수단(테스트·빌드·스크린샷)을 주고, "완료"라고 말하는 대신 **출력을 보이게** 한다.
- diff는 새 컨텍스트의 subagent가 한 번 더 리뷰한다.
- 로컬에서 `/code-review`, `/security-review`를 먼저 돌린다.
- 같은 지적이 반복되면 리뷰 코멘트로 두지 말고 **원천에서 고친다**: 린트 규칙, skill, `CLAUDE.md`·`REVIEW.md`.
  - `CLAUDE.md`: 프로젝트의 스택·관례·목표·비목표. 짧게 유지하고 상세는 다른 문서로 링크한다. 이를 어기는 변경, 이를 낡게 만드는 변경도 지적 대상이다.
  - `REVIEW.md`: 코드 오너가 쓴 리뷰 규정. 짧게, 실패의 정의·Nit 상한·제외 경로·`file:line` 근거·개수로 시작하는 요약을 담는다.

## 2. AI 리뷰 — 모든 PR

- diff를 저장소 전체와 PR이 밝힌 의도에 대조해 읽는다.
- 묻는 것: **문제를 푸는가 / 시스템에 맞는가 / 다른 것을 깨는가.** 버그 수정이면 근본 원인을 찾았는지 본다.
- 지적은 사람에게 보이기 전에 다른 에이전트가 검증한다. 충분히 동의된 것만 남긴다.
- 스타일·진단·정리만인 지적은 버린다.
- 심각도는 `Important` / `Nit` / `Pre-existing`으로 단다. 이번 PR이 만들지 않은 버그가 작성자 탓으로 보이지 않게 한다.
- **모든 지적에 답한다**: 고치거나, 이유를 달아 스레드를 닫는다.
- 리뷰 깊이는 위험에 맞춘다. 놓친 버그 하나가 비싼 곳에만 깊은 리뷰를 쓴다.

### 수렴 — 리뷰가 끝나야 한다

에이전트 작성자와 에이전트 리뷰어는 서로를 끝없이 바쁘게 만들 수 있다.

- **라운드 상한**: 3라운드가 넘으면 작성자에게 접근 방식 자체를 재검토하게 한다.
- 처음 몇 라운드 뒤에는 **새 diff만** 다시 본다.
- 한 줄이 아니라 **버그의 종류**를 지적해, 작성자가 모든 사례를 한 번에 고치게 한다.
- 이미 올린 지적을 **반복하지 않는다**.

### 노이즈

- 버그를 많이 잡는 것만큼 비(非)버그를 적게 지적하는 것이 중요하다. 우선순위: **실제 버그 포착이 먼저, 리뷰 라운드 감소가 다음.**
- 작성자가 에이전트면 노이즈가 더 비싸다. 사람은 Nit을 몇 초 만에 넘기지만, 에이전트는 고치고 커밋해 리뷰를 한 바퀴 더 돌린다.

## 3. 보안 리뷰 — 막을 수 있다

- 보안은 별도의 자동 리뷰를 받는다.
- 버그 리뷰·보안 리뷰의 지적이 하나라도 열려 있으면 머지하지 않는다. 오탐은 짧은 이유를 달아 닫는다.
- 이후 커밋이 문제를 고치면 지적은 저절로 해소된다.

## 4. 자동 검사 — 막는다

- 린트, 타입 검사, 모든 플랫폼의 테스트, 빌드.
- PR 템플릿에 **어떻게 테스트했는지(Testing)**, **위험(Risk)**, **어떻게 되돌리는지(How to revert)**를 묻는다. Claude가 채울 수 있지만 변경을 요청한 사람이 사인오프한다.

## 5. 사람 승인 — 위험에 비례

| 위험 | 예 | 사람 승인 |
|---|---|---|
| Low | 문서, 문구, 내부 전용 기능, 플래그 뒤의 추가 변경 | 자동 리뷰·보안 검사 통과 시 불필요 |
| Medium | 일반 제품 변경, 민감 영역(캐시, 자동 업데이트, 시스템 프롬프트) | 1명 |
| High | 가장 위험한 코드, 항상 두 명이 필요한 경로 | 2명 |

- **등급은 작성자가 아니라 변경이 정한다.** 엄격하게 시작하고 근거가 쌓이면 완화한다.
- 오너가 민감하다고 지정한 경로와 CI 워크플로 파일은 항상 사람이 본다(CODEOWNERS, 브랜치 보호). 인증·결제·CI·릴리스·설치 프로그램이 해당한다.
- 가벼운 승인 경로는 **신뢰된 작성자**에게만 준다.
- **에이전트의 승인은 사람의 승인으로 세지 않는다.** 자기가 작성한 변경을 승인하지 않는다.
- 에이전트가 쓴 PR이면 **에이전트를 지시한 사람**이 필수 리뷰어 중 하나다.
- 승인은 **특정 커밋**에 대한 것이다. 보증할 수 없는 새 커밋(에이전트 push, 손으로 푼 머지)이 오면 다시 승인받는다.

## 6. 머지 큐·플래그·단계적 릴리스

- 머지 큐는 변경을 적용한 main 기준으로 모든 검사를 다시 돌린다. 따로 통과한 두 PR이 합쳐져 main을 깨지 않게 한다.
- 새 동작은 플래그 뒤에 두고 내부 사용자에게 먼저 낸다. 공개 릴리스는 `latest` 채널이 먼저, `stable`이 뒤따른다.

## 7. 빠른 감지·빠른 롤백

- 플래그는 배포 없이 끈다. 되돌리기는 한 단계여야 한다.
- 사고 리뷰는 "**어느 레이어가 이것을 잡았어야 했나**"를 묻는다.
- 사고·revert는 리뷰어의 eval 세트가 된다. 리뷰어의 프롬프트·도구·모델이 바뀌면 다시 채점한다.
- 리뷰가 놓쳤으면 모델 앞에 무엇이 없었는지 묻고, 그 보완을 `CLAUDE.md`·skill·새 검사에 넣는다.
- 사람의 시간을 측정하되, revert·사고율을 가드레일로 둔다. 그것이 오르면 시간을 아낀 게 아니라 옮긴 것이다.

---

## 사람이 맡는 것

- **만들지 말지 결정한다.** 방향·취향·범위. 방향이 다르면 완성된 PR에 막는 코멘트를 달지 말고 스레드에서 **일찍** 말한다.
- **위험한 코드**를 리뷰한다(결제, 자동 업데이트, CI 워크플로).
- **다른 사람이 따라 할 패턴**을 만드는 아키텍처를 리뷰한다.
- **증거를 읽는다.** 테스트 출력, 실행한 명령과 결과, 스크린샷, 리뷰어의 지적. 검사가 무엇을 놓칠지 말할 수 없으면 빠른 승인 대신 제대로 된 리뷰를 요청한다.
- **결과를 책임진다.** 누가 타이핑했든 머지된 모든 변경에는 책임지는 사람이 있다.

## "머지한 사람이 책임진다"를 받치는 조건

- 변경은 **작게**: 리뷰·디버그·revert가 쉽다.
- 모든 것은 **되돌릴 수 있게**: 플래그, revert, 단계적 릴리스.
- **영향 범위가 기준을 정한다**: 비싼 코드일수록 더 많은 사람과 검사.
- 회귀는 텔레메트리·내부 사용으로 **빨리 드러나게**.
- **비난이 아니다**: 고치는 사람은 맥락이 가장 많은 사람이고, 사고 리뷰는 시스템을 본다.
